# 三模型搭配编排方案（实测驱动）

日期：2026-09-13　样本：真实作业照 IMG_A（19.2 实数提高性测试，15 题手写+红笔）
真值：放大原图人工逐题核对（`deliverables/ground_truth_ocr.json`）
判题口径：生产同款 `server/services/judgeService.js` → `judgeAnswer()`（本地规则，不调 AI）
解析口径：生产同款 `repairAIJson()`（从 `server/worker.js` 逐字提取）

---

## 一、结论先行

**能搭配，且搭配严格优于任何单模型。** 三个模型的能力是**正交**的，不是替代关系：

| 模型 | 真正的优势 | 真正的硬伤 |
|---|---|---|
| 魔搭 Qwen3-VL-235B | `student_answer` 抽取全（15/15），关键符号准（Q11 负号唯一正确） | `answer` 字段 15/15 被学生答案污染；坐标框 0% 合法 JSON |
| sensenova-6.8-flash-lite | 快 40%、严格 JSON 3/3、坐标 15/15 合法、零污染 | 漏抽 4 题学生答案；手写在关键符号上会丢（Q11 丢负号） |
| grok-4.5 | 数学等价形式宽容度最高（13 题集 77%），且 0 调用失败 | 视觉链路 66% 成功但 `student_answer` 0/15 全空，**不可用于 OCR**，只能做判题终裁 |
| grok-4.6 | 宽容度次高（73%） | 视觉成功率 2/6；判题 13 题里 2 条调用失败，稳定性不如 4.5 |

**关键判断：不能让 sensenova 单独取代魔搭。** 上一版报告说「sensenova 可以取代魔搭」，本次端到端实测修正了这个结论——sensenova 学生答案准确 8/15 < 魔搭 10/15，且 Q11 丢负号。它的优势在**格式与速度**，不在**内容准确度**。

## 二、核心实测证据

### 2.1 魔搭污染 → 判题假阳性（最严重）

把三方 OCR 结果分别喂生产 `judgeAnswer()`：

| 模型 | 题数 | 有学生答案 | answer 污染 | 可判题 | 判对 | 判错 | 假阳性 |
|---|---|---|---|---|---|---|---|
| ms-235b | 15 | 15 | **15** | 15 | **15** | **0** | **15** |
| sensenova (effort=none) | 15 | 11 | 0 | 0 | 0 | 0 | 0 |

魔搭把 `student_answer` 抄进 `answer` 字段 → `judgeAnswer(学生答案, 学生答案)` → **15 题全部判对、0 判错**。
整张卷子无论学生写什么都会被判全对。这是隐性全卷误判。

**污染为何会生效**：答案来源链路是 `OCR answer → 缓存 → AI 生成 → 答案库 → 判题`（`worker.js:1579/1649/1679/4358`）。
缓存未命中、AI 生成失败早退、答案库归因失败时，OCR 的 `answer` 会一路留到判题器。

### 2.2 双路并行：延迟几乎零代价

| 指标 | 实测 |
|---|---|
| sensenova 单跑 | 51.3s |
| 魔搭单跑 | 80.3s |
| **并行 wall-clock** | **80.3s**（= max 两者，调度开销 0.0s） |
| 串行叠加 | 131.6s |
| **并行节省** | **51.3s（39%）** |

因为并行耗时 = 较慢那一路的耗时 = 魔搭单跑耗时，**双路校验不增加端到端延迟**。

### 2.3 互补性：合并后两项指标同时最优

| 策略 | 耗时 | 有学生答案 | 污染 | 需人工复核 |
|---|---|---|---|---|
| S1 单跑魔搭 | 80.3s | 15/15 | **15** | 0 |
| S2 单跑 sensenova | 51.3s | 11/15 | 0 | 0 |
| S3 并行 + 魔搭补抽 | 80.3s | 15/15 | 0 | 0 |
| **S4 并行 + 补抽 + 分歧标记** | **80.3s** | **15/15** | **0** | **1/15（7%）** |

S4 同时拿到「魔搭的覆盖率」和「sensenova 的洁净度」，耗时与现状持平。

### 2.4 分歧检测抓到了真问题

两者都抽到但不一致的只有 Q11 一处：

| 题 | 真值（放大原图） | sensenova | 魔搭 | 判定 |
|---|---|---|---|---|
| Q11 | `−2√3` | `2√3` ❌ | `-2√3` ✅ | SN错/MS对 |

**这处分歧正是魔搭更准的那类（手写负号）。** 分歧标记把最需要人工看的那 7% 挑了出来，而不是让老师全卷复核。

## 三、搭配方案（三个搭配点）

### 搭配点 1：OCR 双路并行 + 合并闸（推荐，收益最大）

```
作业图
 ├─→ sensenova-6.8-flash-lite (reasoning_effort: 'none')   ← 主干：结构、坐标、answer 洁净
 └─→ 魔搭 Qwen3-VL-235B                                     ← 补抽：student_answer
        ↓ 合并闸（本地，0ms）
   ① 补抽：sensenova 漏抽的 student_answer，用魔搭的补上（+4 题）
   ② 污染闸：norm(answer) === norm(student_answer) → answer 强制置空
   ③ 分歧标记：两者都有值但不相等 → 标 needs_review，送人工
        ↓
   规则判题 judgeAnswer
```

- **耗时**：80.3s（与现状持平，不劣化）
- **收益**：污染 15 → 0，学生答案 11 → 15，并精准标出 7% 需复核题
- **失败降级**：sensenova 失败 → 直接用魔搭结果（+污染闸）；魔搭失败 → 用 sensenova（+补抽跳过）

### 搭配点 2：判题终裁（✅ 已落地 2026-09-13 晚，见下方落地说明）

判题主路径**保持本地规则 `judgeAnswer`，不换模型**（客观题本来就 0ms、0 成本）：

| 层级 | 处理 | 触发条件 | 延迟 |
|---|---|---|---|
| L1 | 规则 `judgeAnswer` | 全部客观题 | 0ms |
| L2 | 魔搭 AI 判题 | L1 判不出（等价写法、单位、多空顺序） | 1.3s |
| L3 | **grok-4.5** 终裁 | L2 仍存疑 / 老师点了「有异议」 | 12.5s |
| L4 | 人工 | 主观题、模型分歧题 | — |

依据：主集（38 条无争议用例）各模型**全部 100%**；差异只在「等价但未化简」这类边界。
13 题等价形式专项同口径复测（2026-09-13）：

| 模型 | 宽容率 | 平均延迟 | 调用失败 |
|---|---|---|---|
| **grok-4.5** | **10/13 = 77%** | 12.5s | **0** |
| grok-4.6 | 8/11 = 73% | 13.4s | 2 |
| 魔搭 235B | 9/13 = 69% | **1.0s** | 0 |
| sensenova | 7/13 = 54% | 2.7s | 0 |

**L3 选 grok-4.5 而不是 4.6**：宽容度更高、更快、且 4.6 有 2 条调用失败。
grok 的 12.5s 只有放在 L3 少量题上才划算；L2 用魔搭（1.0s）兜住大多数。

#### 落地说明（2026-09-13 晚，实际实现与原计划的两处差异）

1. **原计划的 L2「魔搭 AI 判题」层取消**：魔搭当前无可用纯文本模型
   （ai.js:283 实测注释——纯文本请求直接报错），原表里的 1.0s/1.3s 口径不可实现。
   实际链路 = 规则 → grok-4.5 终裁 → 人工（三级）。
2. **「老师点异议再终裁」暂未做**：本次只做批改管线内自动终裁；复核页手动触发留给后续。

实际实现：
- `server/services/aiJudgeService.js`：aiJudgeAnswer（单题终裁）/ selectJudgeCandidates（选题闸门）/
  parseJudgeVerdict（裁决解析，非法输出一律按 uncertain 转人工）。
- `server/config/ai.js`：新增 callVendorTextCompletion（指定供应商+模型；grok 调用必须
  extraBody=null，否则会带上 sensenova 专用的 reasoning_effort:'none'）。
- `server/worker.js`：aiJudgeUncertainQuestions 接入三条批改链路（练习册 / 答案库通用 /
  Step7/8 重判），落库前或 persist 回写；AI 判错的题 confidence 抬到 0.9，
  让错题本置信度闸放行（防"判错了进不了错题本"）。
- 安全边界：仅 choice/fill/judge；未作答/无参考/开放题（"证明略"）不送裁；
  超时 30s；AI_JUDGE_ENABLED=0 一键回滚。
- 冒烟（_bench_ai_judge_smoke.mjs，本机走 socks5 代理，13 道等价/陷阱题）：
  9 题给出结论**全部判对（误判 0）**，4 题代理超时 → 按设计转人工。

### 搭配点 3：按图片类型路由（可选，进一步省时）

| 场景 | 建议 | 依据 |
|---|---|---|
| 印刷清晰卷 / 练习册答案页 | sensenova 单跑 | 17–19s vs 魔搭 26–35s，且魔搭污染在此场景最致命 |
| 手写涂改重的作业照 | 双路并行 | sensenova 漏抽率 27%，必须靠魔搭补 |
| 练习册（有答案库） | 双路并行 | 答案库归因失败时，污染 answer 会直接进判题器 |

## 五、风险与前置条件

1. **网络路径未验证**：`api.huihuiyun.top` 本机直连 `http=000`，全程走代理才通。
   Render（Oregon）能否直连未验证 —— **上线前必须先验**。
2. **sensenova 必须传 `reasoning_effort:'none'`**：默认参数 100% 失败（reasoning 吃掉全部 8192 tokens，正文不吐 JSON）。
3. **成本翻倍**：双路并行 = 两张图都要计费。魔搭免费但有限流（测试期间实测到 429）。
4. **样本量**：真图只有 1 张作业照（15 题）+ 1 张清晰卷。结论方向可信，**比例数字需 50+ 张真图加固**。
5. **真值局限**：IMG_A 有 5 题卷面被红笔划掉/未作答，真值标注存疑，会拉低两边准确率，但不影响「污染」与「互补」两个核心结论。

---

## 六、建议落地顺序

1. **先做污染闸**（不改模型，纯本地断言，风险最低）—— 单独这一项就消除 15/15 假阳性
2. **再做双路并行 + 补抽 + 分歧标记**（`HYBRID_VISION_ENABLED` 开关控制，可灰度）
3. **最后做判题三级瀑布**（grok-4.5 只上 L3 终裁，量小，成本可控）

### 关于 `mimo-v2.5` 与 `hy3`（已用第二把 key 实测，2026-09-13 定稿）

**旧 key（`sk-a4e3…`）下是 404「账号组未开通」**；换第二把 key（免费组，`sk-a1e5…`，清单 6 个模型）
后两者**均能调通**，因此得以完成实测。结论：**双双出局，且 hy3 是最危险的类型**。

**① 视觉模态判定（用同一张白底标准文字图，图中为 `7X49 = 343`）**

| 模型 | 返回 | 判定 |
|---|---|---|
| `sensenova-6.8-flash-lite` | `7X49 = 343` | ✅ 真看到了图 |
| `hy3` | `12 ÷ 3 = 4` | ❌ **图中根本没有，纯幻觉** |
| `mimo-v2.5` | 120s / 180s 超时，0 输出 | ❌ 处理不了图像 |

**② hy3 跑真实作业照（15 题真值）**：9.9s / 7.8s 各输出 **4 题、3 题**，内容全是**二次函数与抛物线**
（真卷是「19.2 实数」，考 √5/√6/绝对值/平方根），且两轮内容互相矛盾。

按 ground truth 逐题核对：**学生答案准确率 0/7 = 0%**。

> hy3 的危险性在于**它不报错**——输出格式合法、JSON 完整、甚至编出了合理的学生答案。
> 相比之下 grok 系列是 502 超时，失败即暴露；hy3 会静默产出看似正确的垃圾。
> 这是唯一一个必须明确「禁止接入」而非「暂不使用」的模型。

**③ 判题能力（文本侧，两个模型基础能力其实没问题）**

| 模型 | 主集（20 条无争议） | 等价形式宽容度（13 条） | 延迟 |
|---|---|---|---|
| grok-4.5 | 100% | **77%** | 12.5s |
| 魔搭 235B | 100% | 69% | 1.0s |
| **hy3** | 100% | 62% | 2–17s |
| **mimo-v2.5** | 100% | 62% | 2–**142s**（极不稳） |
| sensenova | 100% | 54% | 2.7s |

hy3 与 mimo 错的题完全一致（B01/B02/B04/B06/B09/B10），均为「未化简到最简形式」
（√12 vs 2√3、6/10 vs 3/5、4:2 vs 2:1、0.6 vs 3/5），口径一致地严格。
**宽容度 62% 低于 grok-4.5 的 77%，替换不了 L3 终裁。**

**结论：hy3 / mimo-v2.5 均不进入优化组。**
- OCR 链路：hy3 幻觉（0% 准确）、mimo 超时 —— 都不能用
- 判题终裁：宽容度 62% < grok-4.5 77%，且 mimo 延迟 2–142s 无法用于生产

### 关于第二把 key（免费组 `sk-a1e5…`）

清单 6 个模型：`auto（随机路由高级模型）` / `grok-4.5` / `grok-4.6` / `hy3` / `mimo-v2.5` /
`sensenova-6.8-flash-lite`。实测其中**两个已在用模型的质量与旧 key 完全一致**：

| 模型 | 免费组 | 旧 key | 结论 |
|---|---|---|---|
| `sensenova-6.8-flash-lite` | 46–51s，15 题，零污染 | 46–51s，15 题，零污染 | **无差异** |
| `grok-4.5` 等价宽容度 | 10/13 = 77% | 10/13 = 77% | 无差异，但免费组延迟 8–121s 且有 2 次解析失败 |

> ⚠️ 中途曾出现「免费组 sensenova 有答案 15/15、旧 key 只有 11/15」的差异，

### 关于 `deepseek-v4-flash`

**实测结论：这个 key 下不可用**，请求返回 404：

```
Model "deepseek-v4-flash" is not supported by any configured account in this group
```

注意这与 429 限流不同——404 是「该账号组未开通此模型」，重试无效。已排除的近似名：
`deepseek-v4-flash`、`deepseek-v4-flash-lite`、`deepseek-v4`、`deepseek-v3.2-flash` **全部 404**。

官方端点 `token.sensenova.cn` 上的同名模型则返回 429（`tpm/rpm exhausted`），因官方 key 已打满，
**无法验证其是否存在**。如需启用，须先让网关方为该账号组开通，或等官方 key 配额恢复后另行验证。

**即便将来开通，第一件事是确认它是否支持图片输入**——若不支持视觉，则对 OCR 链路无意义，
只能用于判题终裁，届时与 grok-4.5 对比「等价形式宽容度 + 延迟」再决定。
