## 一、结论先行

1. **"错题卷重新生成了答案"不成立**。`processSlimGrading` 对题目行只写
   `student_answer` + `is_correct` + `confidence`，**从不写 `answer`**；`answer` 的赋值链条
   （OCR 卷面印刷答案 → question_cache 指纹缓存 → 答案引擎深解）只在**原作业批改**时跑过。
   判题审计（`judgements.source='ai_ocr'`，9/8–9/10）里的「参考快照」与该生重练时读到的
   `questions.answer` **逐字相同** —— 说明错答案在 9/8–9/10 就已沉淀，重练卷只是继承。
2. **但沉淀下来的是错答案**。这张卷 9 条「AI错误」里，**5 条是误判**，其中 4 条的根因就是
   参考答案本身错/不可用（#4 #5 #7 #12），1 条是解答题根本没判却展示了原作业的旧判定（#10）。
3. **另有一条独立缺陷把学生答案判错**：循环点（U+0307 组合上点）在全链路无处理 ——
   重练卷**打印时循环点整颗丢失**（卷面印成 `2.6`、`3.12`），OCR 学生答案时又丢一次（`0.31̇8̇`→`0.318`）。

## 三、三类根因（含影响面）

### 根因 A：答案解析「抓错句」——45/586 条缓存受影响（7.7%）

答案引擎返回 `{answer, analysis}` 后，`worker.js → extractAnswerFromAnalysis →
utils/aiParseSelfCheck.js:extractFinalAnswerFromAnalysis` 用 8 条正则找「答案标记」，
**取第一个命中**。当模型在解析里自言自语（"……所以正确答案应包含10。……最终答案：2,3,5,6,7,8,10。"），
就抓到了中间那句残句。实测复跑：`extractFinalAnswerFromAnalysis(落库解析)` → `"应包含10"`。

审计脚本（本轮新写）：`.workbuddy` 外不落库，口径=「analysis 里最后一个答案标记」与落库 answer 比对。
结果：**45/586 条缓存不一致**，样本：`应包含10`、`应为这些`、`应为①、④、⑤`、
`“4x+10x²”，可能是题目中…`、`"是"`、`平方根（简称平方）` —— 全是解析残句。

### 根因 B：答案引擎自身幻觉，且自检未拦住

- #4：解析末句「最终答案是 2」（与前文 `√6+2` 冲突）
- #7：解析「a=8，b=3，a+b = 8+3 = 29」
- #12：级数乘 2 时系数算错 → `S = 4`（正确 3）
这些行 `ai_self_check_passed = true`。`aiParseSelfCheck` 在 worker 里接在 OCR 段落
（`worker.js:6310`），**答案入库路径（`updateQuestionAnswer`）没有再复核一次提取结果**。

### 根因 C：循环点 U+0307 全链路无处理（37 道题）

`UPDATE questions SET answer ...` 与题干都原样带 `U+0307`（组合上点）。实测码点：
`如果2.6̇化为…` → `…32 2e 36 **307**…`；`0.1̇2̇×9−1/11` → `30 2e 31 307 32 307…`。

链路三个断点（本轮实测取证）：

1. **出卷打印丢点**：重练答卷照片上第 7 题印的是 `如果2.6化为最简分数后是a/b`、
   第 8 题印的是 `将小数化成分数：3.12=` —— **一个点都没有**。学生按印出来的题作答
   （#7 答 18 = 13/5，正好是 `2.6` 有限小数的答案）。原卷印刷是有点的
   （像素级验证：第 6 题 `3.1̇2̇` 上方只有一颗点且正对末位 `2` → 该题确为 `3.12̇`，`281/90` 正确；
   同卷另一题 `0.1̇2̇` 的点在 1、8 两位上）。
2. **OCR 学生答案丢点**：学生实写 `0.31̇8̇`（点在第 1 位与第 8 位，**写法正确**），
   入库 `0.318`；#11 的 `5.295̇4̇` → `5.2954`。
3. **判等层不认识循环点**：实测 `judgeAnswer('0.31̇8̇','0.31818...','fill') → false`
   （即使参考答案规范成 `0.31818...` 也判不出）。

### 根因 D（附带发现）：解答题的「本次没判」被显示成「AI错误」

`worker.js` slim 落库：`is_correct = COALESCE($2, is_correct)`。主观题（`SUBJECTIVE_TYPES`
含 `answer`）走 manual 分支 → `$2 = null` → **保留原作业的旧 `is_correct`（false）**，
而批改页 6 态（`src/utils/reviewDecision.js`）见 `is_correct===false` 即判 `wrong`（AI错误）。
本卷 4 道解答题因此显示「AI错误」，实际 `tasks.result.retryAlign` 里 `isCorrect = null`（未判）。
本卷更严重的是：批改页展示的**学生答案是重练卷的新答案**，而**判定来自原作业**，两者错配。

## 四、影响面与修复建议（按优先级）

| 优先级 | 项 | 位置 | 建议 |
|---|---|---|---|
| P0 | 解答题未判却显示 AI错误 | `server/worker.js` slim 落库 `COALESCE` | manual 分支显式写 `is_correct = NULL`（或引入「本次未判」标记），并核对 weeklyReport / diagnosisService / knowledgeMasteryService 对 null 的口径 |
| P0 | 答案解析抓错句 | `server/utils/aiParseSelfCheck.js:extractFinalAnswerFromAnalysis` | 改为**取 analysis 里最后一个答案标记**（或限末 200 字），命不中再回退原 answer；`test/judgeService.test.mjs` 加 `应包含10` 回归用例；已污染的 `question_cache`（45 条）用解析重算后刷新 |
| P0 | 答案引擎幻觉答案 | `server/worker.js` 答案入库路径 | 提取结果再过一次 `aiParseSelfCheck` / `validateArithmeticAnswer`，不自洽就**转人工**（`markAnswerException`），不许直接入库 |
| P1 | 循环点 U+0307 全链路 | 出卷渲染（`MathRender`/打印 CSS）、OCR、`judgeService` | ① 出卷/预览前把 `x.1̇2̇` 规范成可打印写法（如 `0.3\overline{18}` 或 `0.\dot{1}\dot{8}`），打印后再自检「题干是否含点」；② 学生答案与题干都做同一套循环小数归一（`0.31̇8̇ → 0.3(18) → 318…`），判等层加「循环小数 ↔ 分数」通道 |
| P1 | 答案可信度不可见 | `questions.answer_source` 只描述**学生**答案 | 建议为参考答案加来源字段（答案库 / 教师录入 / AI 生成），批改页对 AI 生成答案显示弱提示，让老师复核时知道该不该信 |
| P2 | 存量错答案 | `questions.answer` + `question_cache` | 复用 `server/scripts/audit-reference-answer-quality.mjs` 的口径做一次全库体检；本轮 5 条样本题号：`e8188cbc` `849fdf8a` `9a48f92d` `5e1e602b` `e81cb70c` `55190602`（缓存 id：`83365918` `2dd2d2c0` `414e4bfa` `c3c1a622` `97507bc7`） |

> 注意：**改代码不会翻转已入库的判定**（skill「敏学判题误判修复」第 5 条）。
> 本卷 9 条显示为「AI错误」的题，若要立刻在批改页改观，需老师人工改判或走重判接口。
