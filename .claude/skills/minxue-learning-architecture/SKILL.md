# 敏学学习架构

## 职责边界

本 Skill 只回答"决定做之后，应该如何正确接入敏学现有学习架构"：

- 能力属于哪个业务域；
- 应复用哪些现有系统；
- 数据在哪里产生、由谁拥有、谁只读取；
- 哪些操作可以改变学习状态；
- 系统如何形成统一学习闭环；
- 是否需要新增页面、API、Service、字段、数据表或关联表。

不要替代 `minxue-product-review` skill 判断真实需求、产品价值、是否应该做或最小产品方案。若需求尚未完成产品评审，应明确区分产品判断与架构判断。

## 触发后的准备

默认只读分析，不修改业务代码、数据库、迁移、`AGENTS.md` 或 `docs/`。

每次触发后优先读取以下文件：

- `AGENTS.md`
- `docs/architecture.md`
- `docs/grading-flow.md`
- `docs/wrong-question-system.md`
- `docs/knowledge-system.md`
- `docs/handout-system.md`

问题涉及具体实现时，再按需只读相关路由、Service、Worker、Schema 和迁移。以项目文档和实际代码为事实来源；文档未覆盖的内容标为"尚未确认"或"需要核实"，不要猜测成现状。

## 核心事实归属

坚持"一类事实一个主要来源"：

- 正式判题结果：批改流程和 `judgements`；
- 学生作答题目：`questions`；
- 学生具体错题：`wrong_questions`；
- 题目与知识点关系：`question_knowledge`；
- 学生知识点掌握状态：`knowledge_mastery`；
- 讲义内容、结构和脚本：讲义系统及 `handout_lectures`；
- 变式题：`variant_questions`；
- 组卷与重练题目集合：`generated_exams`；
- 任务执行与上传状态：`tasks`。

展示层、诊断报告、成长中心、家长端和未来 Agent 主要聚合、解释、展示或提供行动入口，不能复制并维护另一套错题、掌握度或学习状态事实。

## 学习闭环原则

分析任何跨系统需求时，沿着这条链路检查：

```text
学习事实
  -> 学习问题
  -> 教学需求
  -> 讲义或其他教学干预
  -> 重练或知识点验证
  -> 正式练习与判题
  -> 错题/知识点学习证据
  -> 学习状态变化
  -> 下一轮教学决策
```

必须保持以下边界：

1. 打开、阅读或展示讲义不等于知识点掌握，也不等于错题解决。
2. 只有正式练习和正式判题结果，才能影响错题、掌握度或练习记录。
3. 错题生命周期和知识点掌握度是两个独立状态，互相提供证据但不能直接覆盖。
4. 知识点重练答错不应批量制造错题；只有具体题目满足现有错题规则时，才进入错题流程。
5. 知识点重练答对不应自动解决全部相关错题。
6. 诊断、成长展示和家长端不能成为新的学习事实写入者。

## 强制分析流程

按以下顺序分析，不要跳到表结构或接口设计：

1. 列出当前涉及的业务系统。
2. 说明每个系统的职责和不应承担的职责。
3. 追踪每类数据的产生位置、主要来源和最终归属。
4. 区分写入系统、只读系统、聚合系统和行动入口。
5. 列出哪些操作可以改变 `wrong_questions`、`knowledge_mastery`、retry records 和 teaching needs。
6. 列出哪些操作不能直接改变这些状态。
7. 描述从学习事实到下一轮教学决策的数据流，必要时使用 Mermaid。
8. 检查是否出现重复的题目、判题、错题、知识点、掌握度或任务数据系统。
9. 分别判断是否需要新增页面、API、Service、字段、数据表或关联表。
10. 判断能否先复用现有批改 Worker、`tasks`、`questions`、`judgements`、错题、知识点、组卷、变式题和讲义能力完成 MVP。

## 系统职责参考

按当前项目文档理解边界，不要因新概念擅自拆出平行系统：

- 作业批改：接收学习材料，完成 OCR、判题和正式结果写入。
- 错题系统：承载具体错题、错误次数、练习次数和错题生命周期。
- 知识点系统：承载题目关联、知识树匹配和学生掌握度。
- 错题重练：验证具体错题是否改善。
- 知识点重练：验证知识点是否能在新题或变式题中迁移。
- 讲义系统：承载解释、例题、变式题、脚本和导出内容。
- 组卷与任务：组织题目集合、上传和批改执行状态。
- 诊断报告：基于既有学习证据做周期性分析和解释。
- 成长中心：聚合成长信息并提供展示和行动入口，不拥有新的学习事实。
- 家长端：按授权读取和解释学生学习信息，不复制核心学习状态。
- Agent：调用现有领域能力进行诊断、教学、组卷或行动编排，不直接绕过领域写入规则。

## 状态变化规则

明确写出：

- 什么正式判题结果可以新增、更新或推进 `wrong_questions`；
- 什么已确认的练习结果可以更新 `knowledge_mastery`；
- 什么任务或练习结果可以写入 retry records；
- 什么诊断结果可以形成 teaching needs；
- 哪些阅读、展示、推荐、打开页面或 Agent 观察行为不能直接写入以上状态。

跨域反馈必须通过拥有该状态的系统完成，其他系统只能提供来源引用、聚合结果或待执行动作。

## 固定输出格式

每次架构分析必须完整包含以下标题：

## 架构结论

说明能力应归属、复用、扩展或隔离到哪个已有业务域；不要在这里重新做产品价值评审。

## 涉及的业务系统

列出实际涉及的系统，并标明直接参与、间接读取或暂不涉及。

## 系统职责划分

说明各系统负责什么、不负责什么，以及最终状态由谁拥有。

## 数据来源与归属

列出数据产生位置、主数据来源、写入者、只读引用和跨系统反馈方向。

## 系统之间的数据流

使用 Mermaid 或清晰的文本流程，覆盖学习事实、教学需求、教学干预、训练验证、判题和下一轮决策。

## 状态变化规则

分别说明 `wrong_questions`、`knowledge_mastery`、retry records 和 teaching needs 的可写入条件，以及禁止直接写入的操作。

## 是否存在重复建设风险

检查是否复制已有题目、判题、任务、知识点、掌握度、错题或展示事实。

## 推荐的最小架构

给出在现有系统边界内的最小接入方式，以及只在必要时新增的组件。

## MVP 是否需要新增数据模型

说明是否可以复用现有结构；如果需要新增，解释现有结构为什么无法承担，并区分字段、关联表和独立模型。

## 禁止事项

列出当前阶段不能做的跨域写入、重复存储、平行 Worker、平行掌握度或过早拆分。

## 开发优先级

按 `P0`、`P1`、`P2`、`P3` 说明前置条件、实施顺序、验证点和需要确认的核心流程影响。

## 最终架构建议

用简短结论说明推荐的系统归属、数据流和下一步；若涉及数据库或核心流程，停在方案与影响范围，等待确认。

## 修改纪律

- 除非用户明确要求"按照这个方案开始实现"或"修改代码"，否则停止在架构分析阶段。
- 即使用户要求实现，也先说明影响范围、数据归属、兼容策略和验证方式，并遵守项目 `AGENTS.md`。
- 不修改项目业务代码、数据库、迁移、`AGENTS.md` 或 `docs/`，除非用户明确授权且已完成方案确认。
- 不把推断写成当前系统事实，不假设未确认的表、API 或状态机存在。
