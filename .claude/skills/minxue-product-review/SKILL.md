# 敏学产品评审

## 目标

在开发前把产品想法转化为可验证的架构判断。默认先评审，不创建代码、不修改数据库、不直接拆分独立系统。

敏学当前的核心业务事实和边界以项目内文档为准。触发后先读取：

- `AGENTS.md`
- `docs/architecture.md`
- `docs/grading-flow.md`
- `docs/wrong-question-system.md`
- `docs/knowledge-system.md`
- `docs/handout-system.md`

如果文档不存在、内容不足或与用户描述冲突，明确标注不确定性，并在必要时提出需要补充的事实；不要把推测写成当前系统事实。

## 评审流程

按以下顺序分析：

1. 明确需求要解决的真实问题、目标用户、使用时机和成功标准。
2. 判断需求属于哪个业务域：
   - 学习事实 / 学习证据
   - 学习诊断
   - 教学需求
   - 教学内容
   - 训练验证
   - 成长展示 / 行动入口
   - 或其他已有业务域
3. 检查错题、知识点、掌握度、讲义、重练、任务、组卷、答案库和诊断能力是否已经覆盖需求。
4. 判断应采用哪种路径：
   - 复用现有能力
   - 扩展现有系统
   - 新增轻量能力
   - 暂时不建议做
5. 明确数据来源、数据归属、状态归属和最终写入位置。
6. 分别判断是否需要新增：
   - 页面
   - API
   - 服务
   - 数据模型
   - 数据表
7. 设计最小可落地 MVP，优先使用现有数据和流程。
8. 明确不应该做什么，特别是重复建设、重复存储、跨域写状态和过早拆分系统。
9. 给出实施优先级、主要风险、验证条件和需要负责人确认的事项。

## 关键判断原则

- 新概念不等于新系统；先找现有归属和可复用能力。
- 新页面不等于新业务系统；区分展示层、行动入口和核心数据模型。
- 不为了实现方便复制错题、知识点、掌握度、讲义、任务或判题数据。
- 错题系统主要承载学习事实、判题证据、错题生命周期和练习结果。
- 知识点系统主要承载题目关联、学生掌握度和诊断依据。
- 讲义系统主要承载教学内容、讲义结构、脚本、变式题和导出。
- 重练系统主要承载训练验证；正式判题结果才能反馈学习状态。
- 诊断和成长展示应优先作为已有数据的分析或聚合层。
- 讲义阅读、页面打开或展示行为不能直接替代正式学习结果。
- 练习册答案必须尊重单元、章节、题号、小题号和审核状态。
- 修改核心流程、公共 API、状态机、JSONB 结构或数据库前，必须先说明方案、影响范围、兼容策略和验证方式，等待确认。

## 领域关系检查

评审时至少说明新需求与以下系统的关系：

```text
学习事实/错题
    -> 知识点关联与掌握度
    -> 诊断/教学需求
    -> 讲义与教学内容
    -> 重练/训练验证
    -> 新的判题结果与掌握度变化
    -> 成长展示和下一步行动
```

如果需求跨越多个系统，明确哪个系统拥有最终状态，其他系统只保存引用、快照或展示结果。

## 固定输出格式

评审结果必须包含以下标题，不能省略：

## 结论

明确建议复用、扩展、新增轻量能力，还是暂缓。

## 要解决的真实问题

说明目标用户、当前痛点、触发场景，以及不做该需求的影响。

## 与现有系统的关系

说明所属业务域，并说明与错题系统、知识点系统、讲义系统、重练系统、成长中心、诊断报告等现有能力的输入输出关系。

## 是否存在重复建设

列出已经存在的相似能力、可以复用的模块，以及可能产生的数据或页面重复。

## 推荐方案

给出业务边界、系统归属、复用方式和必要的扩展点。必要时用数据流或 Mermaid 图表达。

## MVP

说明最小用户价值、最小流程、数据来源、页面范围和验证指标。优先不新增数据库。

## 数据与业务边界

明确数据来源、数据所有者、状态写入者、只读引用和跨系统反馈规则。

## 暂时不建议做什么

明确暂不新增的页面、系统、表、状态、自动化或游戏化能力，并说明理由。

## 开发优先级

按 P0、P1、P2 或其他清晰顺序列出实施步骤、前置条件和确认点。

## 最终建议

用简短结论说明是否进入产品设计、技术方案或开发阶段。

## 输出纪律

- 这是产品和架构评审，不是开发任务；除非用户明确要求，否则不要写代码、修改文件或开始实现。
- 事实、推断和建议必须分开表达。
- 对当前文档没有覆盖的内容，使用"尚未确认"或"需要核实"，不要假设已有表或接口。
- 如果需求价值不足、数据基础不足、与现有能力重复或边界不清，应明确建议暂缓。
- 如果涉及数据库或核心流程，先输出方案和影响范围，等待确认后再进入实现。
- 评审结束时说明未修改任何文件；如果用户随后要求开发，重新执行影响分析并遵守项目 `AGENTS.md`。
