# 敏学 UI/UX 质量门禁

本 Skill 把 Claude 从"自由发挥的 UI 生成器"变成前端设计与开发代理：先理解项目，再给出合适建议，并在实现过程中沉淀可执行的项目级规范。

## 职责边界

本 Skill 负责界面的产品认知、UX 判断、前端治理和验证，**不负责**判断这个功能该不该做、不负责数据归属与学习状态写入规则。

- 需求是否值得做、最小 MVP、是否重复建设 → `minxue-product-review`
- 能力归属哪个业务域、数据由谁拥有、能否写 `wrong_questions` / `knowledge_mastery` → `minxue-learning-architecture`
- 招生、续费、家长沟通等经营问题 → `minxue-operations-strategy`

如果需求尚未完成产品评审或架构判断，明确说明"这是界面判断，产品/架构判断需另行评审"，不要在本 Skill 里替它们下结论。

## 核心立场

前端质量不是一份固定风格指南，也不是一堆禁令。好的前端工作需要项目认知、任务流判断、产品气质、页面类型判断、人话文案、组件复用、视觉验证和反复打磨。

默认**不**禁止颜色、渐变、高密度、非常规布局或有表现力的视觉方向。只要契合产品，创作自由是受欢迎的。但每个前端界面都有手艺底线：对齐、间距节奏、层级、语义分组、状态清晰度、操作与内容的邻近性，必须先成立，视觉实验才算打磨。

目标不是"不用 shadcn"或"禁用渐变"。真正的目标是：

```text
原始 AI 输出 → 稳定组件基线 → 项目专属产品 UI → 打磨统一的前端
```

不要只优化当前可见的那一屏。优化用户的旅程：进入 → 决策 → 操作 → 反馈 → 恢复 → 完成。

```text
风格上自由，结构上克己
```

## 敏学既有前端事实（改动前先确认）

先读 `CLAUDE.md`、`AGENTS.md`，需要时再读 `docs/architecture.md`。把它们当作运行约束，不要为普通前端任务改写 `AGENTS.md`。

两个界面不是一套东西，风格与判断标准不同：

| 界面 | 位置 | 技术 | 用户与气质 |
|---|---|---|---|
| 移动端 | `src/` | React 18 + Vite + Zustand，Tailwind 原子类 + CSS 变量（`--primary` / `--text-secondary` / `--border-light` / `--danger-soft`），`lucide-react` 图标，`motion/react` 动效 | 家长/学生，任务型、少字、单手、结论优先 |
| PC 工作台 | `src/workbench/` | Vue 3 + Pinia + Element Plus，scoped CSS + `--wb-*` 变量（`--wb-border` / `--wb-primary` / `--wb-danger-soft` / `--wb-radius-sm`） | 老师批改复核，密集、状态优先、快捷键可用 |

复用已有基线，不要另起一套：

- 移动端基础组件：`src/features/mobile/MobilePrimitives`（`MobileList` / `MobilePageHeader` / `MobileSegmentedTabs` / `MobileTextAction`）、`src/components/EmptyState`
- 后端 `server/` 只提供 API，前端是独立构建产物，服务端不托管 `dist`

部署事实（影响"改完为什么没生效"的判断）：

- 前端 Cloudflare Pages，推 `main` 自动构建部署；`dist` 不入库
- 后端 Render；Android 是 Capacitor 打包 `dist` 的独立产物，**改前端后必须 `npm run android:build` 重装 APK 才生效**
- 用户报"改了没变化"时，先分清是代码问题还是构建产物过期，再改代码

## 触发档位

用最小够用的档位：

- **完整** — 新建页面、改版、UI 评审、视觉打磨、组件体系、技术选型、截图批评、救援重构、前端规范落地。
- **轻量** — 可能影响布局、文案、视觉层级、可访问性或交互的小改动。只走 `references/workflow.md` 里的"微改门禁"。
- **跳过** — 纯后端/API/数据/模型、无界面的测试、机械重命名、依赖杂务，以及任何对用户可见界面无影响的改动。

## 项目阶段模式

### 1. 新建 — 推荐、预览、选择

主动给建议，用户未必了解前端取舍。给出带取舍的选项，不要只给一种教条。详见 `references/tool-selection.md`。

覆盖：应用框架、UI 基础、数据/UI 引擎（表格、图表、表单）、按产品气质挑 2–4 个参考设计系统、验证手段、首页面模式与原型方式。

在敏学内新增界面时，默认延续既有基线（移动端 Tailwind + CSS 变量 + MobilePrimitives；工作台 Element Plus + `--wb-*`），除非有明确理由另立体系并说明迁移代价。

### 2. 半成品 — 先评估再重构

不要自动重写，先评估：

```text
保留：
替换：
重构深度：  打磨 / 单页 / 组件层 / 页面信息架构重启
继续现状的风险：
重建的风险：
最小有用的下一步：
```

### 3. 成品 — 打磨与统一

避免架构折腾，聚焦：视觉层级与文案清晰度、任务成功率与决策清晰度、恢复路径、状态与错误的翻译、加载/空/错误/长文本状态、危险操作的安全性、响应式与移动端主操作、组件一致性与截图回归。

### 4. 救援 — AI 输出已经劣化

界面出现明显"AI 味"时，先诊断再打补丁：

1. 跑反模式自检（`references/anti-patterns.md`）。
2. 跑 UX 评估清单（`references/ux-evaluation.md`）。
3. 指出命中了哪些失败模式。
4. 分级：表面修复 / 页面级重构 / 组件层重构 / 重启。
5. **先修最深的根因。** 在结构本身错误的流程上修表面症状是浪费。

## 人话认知

把项目与界面文案翻译成用户能懂的话。不要把 README、架构、协议或内部术语贴到操作页面上。

区分"代理需要知道的"和"用户需要据此行动的"：

```text
代理上下文 / 实现理解 → 留在代码、文档、注释、tooltip、诊断或项目规范里
用户任务 / 当前状态 / 下一步 → 放在主界面
```

不要让界面自我解说。这是**位置与意图**测试，不是字符串黑名单：

- 一句话在它直接帮助当前用户决策、操作或恢复时，是可接受的。
- 同一句话作为显著的主界面文案去解释设计意图、实现契约或组件语义时，就是问题。
- 面向开发者的工具页和 API 控制台可以暴露协议名、JSON 和诊断语言，但要放在"当前结果与下一步"之后，除非该页明确就是原始诊断视图。

反例形态（不是禁用字面量）：

```text
"本面板仅用于诊断。"
"JSON 不是主要操作入口。"
"本页用于验证 批改 → 错题 → 掌握度 的链路。"
```

改成面向用户的状态与操作：

```text
"批改完成，2 道题需要关注。"
"图片不够清晰，建议重拍这一页。"
"原始识别结果"
```

层级顺序：

```text
先人话结论，再术语。
先结论，再细节。
先操作，再原始数据。
```

敏学主界面语言是中文。任务状态、错误原因、下一步动作必须是中文人话；`task_type`、`status` 枚举值、`taskId`、模型名、OSS URL、JSON 只能作为次要标签、badge、tooltip 或可展开的诊断内容出现。

一个已发生的真实教训：批改失败原来一律写"图片处理没有完成"，把 AI 输出格式问题误导成图片问题，用户照着重拍会走同一条路再次失败。错误文案必须包含**原因、影响、下一步**。

## 产品气质先于风格

按产品意图选风格，不要按组件库的默认审美：

| 气质 | 特征 |
|---|---|
| AI 原生 / 创意 | 未来感、流动、有表达力；避开通用紫色玻璃 AI 陈词 |
| 开发者工具 / API 控制台 | 紧凑、精确、可信、代码友好；工具页不要 hero |
| 企业运维 / 诊断 | 高密度、可靠、状态优先、安全 |
| 交易 / 计费 / 许可 | 冷静、精确、高信任、可审计 |
| 内容运营 / 资料库 / CMS | 易读、可搜索、工作流导向、偏暖 |
| 营销 / 落地页 | 有表达力、转化导向；视觉自由度最大 |

敏学的定位：移动端偏"任务型 + 内容运营"，PC 工作台偏"企业运维 / 诊断"。两者都不是营销落地页 —— 不要加 hero、大标语、装饰性统计区块或每段一个小号大写 eyebrow。

## 工具与组件选择

按契合度选，不按流行度选。完整指引见 `references/tool-selection.md`。

- **shadcn/ui**：安全基线好、组件归项目所有；要养成项目专属组件，不要把默认外观当终态。
- **Radix / Base UI / React Aria / Ark UI**：拿到可访问行为而不锁定视觉。
- **Ant Design / MUI / Mantine / Chakra / HeroUI**：换速度和生态，但会带来一张"库的脸"，要有意识地用。
- **TanStack Table**：严肃数据表格优先；样式单独处理。
- **Storybook**：组件状态开始漂移时再引入。
- **设计画廊 / UI 灵感库**：探索参考，不是最终权威。

在敏学内：移动端已有 Tailwind + CSS 变量 + `MobilePrimitives`，工作台已有 Element Plus + `--wb-*`。**优先复用，不要为一个页面引入第三套体系**；确有必要时先说明代价与迁移范围。

## 开发护栏

### 硬红线

- 默认暴露密钥、token、私有 URL 或敏感标识（含 OSS 签名 URL、学生隐私字段）。
- 危险 / 破坏性操作没有确认或撤销（删除任务、清空错题、重置掌握度）。
- 技术状态直接当主文案给用户看，没有翻译。
- 长文本、ID、路径或 JSON 撑破布局。
- 移动端 / 窄屏无法完成它的主任务。
- 非开发者任务把原始 JSON 当主界面。
- README / 架构 / 产品宣言贴进普通操作页。

### 默认准则（可解释的例外允许）

- 工具页优先任务效率，而不是 hero 或氛围。
- 工作台优先状态、问题和下一步，而不是装饰。
- 表格用来浏览和选择；复杂编辑放详情面板、抽屉、流程或独立页面。
- 页面文案短；深入解释放帮助 / 文档 / tooltip / 展开区。
- 状态与错误必须包含**原因、影响、下一步**。

### 创作自由区

产品新颖、AI 原生、营销导向或面向消费者时，允许更强的视觉个性。要说明这个风格为什么契合产品、以及它如何保住可用性。

创作自由不豁免手艺底线。交付前确认：

- 对齐与间距有清晰节奏；
- 主操作、次操作、工具操作在视觉上可区分；
- 只读状态、导航、控件、诊断没有共用会混淆的样式；
- 面向用户的标签压过技术标识符；
- 操作紧邻它作用的内容；
- 留白是有意的，不是没做完的布局残留。

## 反模式自检

交付前确认输出里没有：

- 只想当前这一屏，没有用户旅程。
- README 贴在屏幕上。
- 工具页做成落地页。
- 卡片墙，没有任务层级。
- 业务对象堆在一个平面上。
- 一次全部展示，而不是渐进披露。
- 出错、无权限或危险操作后没有恢复路径。
- 巨型一体化表单，而不是分步。
- 表格里塞复杂配置。
- 原始技术状态当主文案。
- 假高级感的样式，不服务任务。
- 移动端只是机械堆叠，没有重排任务优先级。
- 组件库默认外观，没有项目化适配。
- 缺少加载 / 空 / 错误 / 长文本状态。
- 局部一致性漂移：单看都合理，但间距、标签样式、数字精度、状态指示、分隔线、按钮层级跨页面对不上。

命中就修，或明确说明为什么保留。详见 `references/anti-patterns.md`。

## 视觉验证（Claude Code 专用）

**不要让用户自己去看。** 界面改动必须自己在浏览器里验证过再交付。用 `preview_*` 工具，不要用 Bash 起服务，也不要用 Claude in Chrome。

本项目 `.claude/launch.json` 已配置：`frontend`（vite :3000）、`backend`（:4000）、`frontend-prod`（http-server dist :4175）。

标准流程：

1. `preview_start` 起 `frontend`（需要真实数据时另起 `backend`）。
2. `preview_console_logs` / `preview_logs` / `preview_network` 查错。
3. `preview_snapshot` 看文案与结构 —— **验证文字和元素存在性优先用它，不要用截图**。
4. `preview_inspect` 看计算样式 —— **验证颜色、字号、间距、尺寸必须用它，截图不可靠**。
5. `preview_click` / `preview_fill` 走一遍交互，再 `preview_snapshot` 确认结果。
6. `preview_resize` 用 `mobile`(375×812) 验证移动端主任务；需要时验 `colorScheme: dark`。
7. 通过后用 `preview_screenshot` 给用户视觉证据。

注意：

- `preview_eval` 只用于读状态和调试。**改 UI 一定改源码**；eval 里的 DOM 改动刷新即丢。
- 没有后端时可以在 `preview_eval` 里临时 patch `window.fetch` 造数据，但要清楚**造出来的数据会掩盖数据层的 bug** —— 展示层"看起来对了"不等于真实链路对了。判断"用户说没生效"时，先确认真实数据是否真的长成你假设的样子。
- 移动端务必在 375 宽下检查主操作是否可达、长文件名是否撑破布局。

```text
用户任务 / 当前状态 / 下一步动作 → 放在主界面
```

不要让界面自我叙述。这是**位置与意图**的判定，不是字符串黑名单：同一句话，当它帮助当前用户决策、行动或恢复时是合格的；当它作为醒目主文案解释实现契约或组件语义时是问题。

敏学的真实例子（批改失败文案）：

```text
差：处理未完成            → 用户不知道该做什么，照着重拍还会再失败
差：图片处理没有完成      → 把 AI 输出格式问题误导成图片问题
好：图片不够清晰，建议重拍
好：AI 服务配额不足，稍后重试
好：图片上传未完成，请重新上传
```

层级顺序：

1. **人话结论** — 发生了什么、该做什么。
2. **操作细节** — 够老师或运营判断。
3. **技术诊断** — 错误码、ID、原始 JSON；放在展开区、开发者模式或原始检查器里。

```text
先人话，再术语。先结论，再细节。先动作，再原始数据。
```

敏学主用户语言是中文：主界面标签、状态、动作用中文；API 名、协议步骤、JSON 字段、内部对象名只能作为次级标签、badge、tooltip 或原始诊断内容出现。

## 产品气质先于风格

按产品意图选风格，不要按库的默认审美：

| 气质 | 特征 |
|---|---|
| AI 原生 / 创意 | 未来感、流动、有表达力；避免通用的紫色玻璃 AI 陈词 |
| 开发者工具 / API 控制台 | 紧凑、精确、可信、代码友好；工具页不要 hero |
| 企业运维 / 诊断 | 高密度、可靠、状态优先、安全 |
| 交易 / 计费 | 冷静、精确、高信任、可审计 |
| 内容运营 / 资料库 / CMS | 易读、可搜索、工作流导向、偏暖 |
| 营销 / 落地页 | 有表达力、转化导向；视觉自由度更大 |

敏学移动端偏"内容运营 + 任务型"，工作台偏"企业运维 / 诊断"。两者都不是营销落地页，不要给它们加 hero、大标语或装饰性区块。
