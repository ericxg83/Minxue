# 本机两份技能库的**正确关系**（2026-10-04，含一次自我纠正）

> ⚠️ **先纠正我自己**：本文档第一版把两份技能库判断成「重复/冗余，建议合并或废弃其一」，
> 并据此提了 P5。**那个判断是错的**——我没有先验证「谁加载哪一份」就下了结论。
> 下面是补做了证据链之后的**正确关系**。**结论：不要合并，也不要删除任何一份。**

## 一、决定性证据：两份服务**不同的消费者**

| 判据 | `~/.workbuddy/skills/`（20 个） | `~/.workbuddy-ai/skills/`（13 个） |
|---|---|---|
| frontmatter 的 `name:` | **中文**（`敏学产品评审`、`敏学并行巡检循环`、`试卷红笔批改诊断`） | **英文**（`minxue-product-review`、`minxue-loop-handoff`） |
| `description_en` 字段 | 有 | 无 |
| 被谁加载 | **WorkBuddy 桌面应用** | **本 Agent 会话** |

加载方的证据：

1. 桌面应用的技能清单缓存 `~/.workbuddy/.skill-list-cache.json`（2026-10-04 12:40 写入，
   共 46 条含插件技能）里的 `name` **全部是中文名**，且**只**引用
   `C:\Users\Administrator\.workbuddy\skills`，对 `workbuddy-ai` 的引用次数为 **0**。
2. 用 `-ai` 独有的技能去缓存里找（答案引擎 / 供应商切换 / 配图输出 / review-bbox /
   workbench-ui-verify / answer-engine）：**命中 0 条**。
3. 本会话的 `<available_skills>` 指向 `C:\Users\Administrator\.workbuddy-ai\skills\...`。

⇒ 两份是**两套各自演化的技能库，各喂一个消费者**。合并会把桌面应用那份改掉、
归档会直接删掉它的技能。**两者都要保留。**

## 二、重叠其实很小

- **同名目录只有 1 对**：`minxue-product-review`（中文名「敏学产品评审」vs 英文名
  `minxue-product-review`，内容不同——各自服务自己的消费者，**可以并存**）。
- 其余是「名字不同、主题相近」：`minxue-model-benchmark` ↔ `minxue-vision-model-benchmark`、
  `minxue-caliber-reconcile` ↔ `minxue-caliber-drift-audit`、
  `minxue-question-element-backfill` ↔ `minxue-question-element-gap`。
  它们面向不同消费者，**不是同一件事的两份**，无需强行统一。
- 两边各有对方没有的技能（`-ai` 侧：答案引擎 / 移动端实测 / 复核定位框 / 工作台实测 / OCR 剪贴板；
  应用侧：几何标注排查 / 判题误判修复 / 冷启动排查 / 并行巡检 / 红笔批改诊断 / PPT 等）。

## 三、所以 P5 的正确处理

| 原 P5 建议 | 纠正后 |
|---|---|
| 以 `-ai` 为准，迁入对方独有技能，归档旧目录 | ❌ **不做** —— 会破坏桌面应用的技能 |
| — | ✅ **两份都保留**；只在**同一件事**上出现矛盾时才需要人工对齐 |
| — | ✅ 新增技能时**先想清楚它服务哪个消费者**，再决定放进哪一份 |

> 真正的风险不是「有两份」，而是「**改错了一份**」：写规则时以为改的是加载中的那份。
> 因此 `minxue-loop-handoff` 技能已补 §9 说明——**改技能前先确认路径**。
