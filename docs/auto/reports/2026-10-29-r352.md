## 核查一：fetchKnowledgeDiagnosis per-student 批量 PDF 潜在 N+1（先证再动 → 止损）
- **实测路径**：前端 `generateAllWeeklyReports`（`src/utils/weeklyReportGenerator.js:1470`）先拉全班 summary 端点（r351 已折成 4 条 `GROUP BY student_id` 批量查询），然后 `for` 循环对每个学生调 `generateWeeklyReport` → `fetch(${API_BASE}/weekly-report/${studentId})`（`weeklyReportGenerator.js:1386`）。
- **逐学生端点代价**：`fetchStudentWeeklyReport`（路由 `server/routes/weeklyReport.js:512`）单次约 **15 条**查询：heal 自愈(1) + tasks(1) + questions(1) + wrong-status(1) + wrong-count(1) + wrong-ids(1) + knowledgeDiagnosis(1) + trend±span/bucket(1~2) + dailyAccuracy(1) + subjectAcc(1) + errorType(1) + `fetchPeriodCompare`(4，含其自身 knowledgeDiagnosis) + `fetchRetryProgress` + retryHistory(1)。
- **结论**：`fetchKnowledgeDiagnosis` 仅是每个学生 ≈15 条查询中的 **1 条**。批量 PDF 路径必须逐学生取「重练卷题 ID / 错因分布 / 学科诊断 / 上一周期对比 / 重练进步时间线」等 summary 端点**不提供**的富数据 ⇒ 逐学生 HTTP 循环是结构固有、不可消除。
- **处置**：把 knowledgeDiagnosis 折进 summary 端点（仿 r351）只能省每个学生 1 条查询，却要改 summary 响应体形状 + 前端改走批量知识诊断，引入跨 API/前端行为漂移风险，收益/风险不成正比。判定为**非缺陷、不擅改（止损）**，属「每轮只落地一件」核查面，留档防下轮重犯（C 级公共 API 变更，拿不准按 B/C）。
- **附带发现**：shareCard 链路 `fetchHasEverGraded`（`shareCard.js:41`）对同学生在 `fetchStudentWeeklyReport` 已按周期自愈后，再用 `epoch→now` 全历史范围再自愈一次。两 heal 范围不同、幂等 best-effort、无行为缺陷，亦非缺陷、不擅改。批量 PDF 路径下 summary 已用 `null` 全班自愈一次、逐学生端点又各自自愈一次（共 N+1 次），同样幂等无害、非行为缺陷，收敛属 C 级行为变更，只提案不擅动。
