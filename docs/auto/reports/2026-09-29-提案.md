## 提案 1：两个失败单测的口径判定 —— 证据指向「实现对、断言过时」（待拍板）

`test/geometryPrimitives.test.mjs:78` 与 `:86` 期望 SVG `sweep-flag = 1`，实际输出 `0`。
四条独立证据均指向实现正确：

1. **提交 5c2ae7f（2026-09-27「配图目标模式——确定性构造管线 + 弧镜像修复」）是故意的改动**：
   `server/utils/geometrySvg.js` 里 `arcPathD` 由 `A r r 0 ${largeArc} 1` 改为 `... ${largeArc} 0`，
   并附注释：「曾误写 1 导致圆心被镜像到弦的另一侧，所有 <180° 的弧都画在错误一侧」。
2. **有真实图形实证**：注释写明由 `622afd21` 构造图实证，且「此前库内从未有成功发布的弧，零回溯影响」。
3. **已有专项回归测试锁住新口径**：`test/geometryArcSweep.test.mjs`（同次提交新增 72 行）不但断言
   `sweep=0`，还用圆心距验证「弧与数学坐标点同侧」，是比正则更强的判据。
4. **本次人工坐标复算一致**：`O(0,0) / A(10,0) / B(0,10)` → 实际输出
   `M 314 264 A 228 228 0 0 0 86 36`。`largeArc=0, sweep=0` 对应圆心恰为 O 的映射位置 (86,264)，
   弧凸向右上；若按断言取 `sweep=1`，圆心会被选到 (314,36) —— 正是要修的那个 bug。

**建议动作（需负责人同意后执行，属于改断言，不在只读巡检权限内）**：

- 把 `geometryPrimitives.test.mjs:83` 与 `:99` 的正则由 `0 0 1` / `0 1 1` 改为 `0 0 0` / `0 1 0`。
  断言仍精确到 flag 位，不是删除或放宽；行为闸由 `geometryArcSweep.test.mjs` 更强地锁住。
- **同时修一处过时注释**：`server/utils/geometrySvg.js:587` 仍写着「数学逆时针 = SVG 顺时针，
  sweep-flag 固定为 1」，与第 618 行的新注释和代码直接矛盾，会误导下一个改这里的人。

影响范围：仅几何重绘 SVG 弧的 path flag 与测试断言，不触碰数据库、不触碰批改判定。
历史数据兼容：无需迁移——5c2ae7f 注释已确认库内此前从未有成功发布的弧。
验证方式：`npm test` 全绿 + `geometryArcSweep.test.mjs` 保持通过 + 抽查一张含弧配图的目视比对。

## 提案 2：三个 P0 已逐条读源码核实（结论同步在 `docs/auto/backlog.md`）

### `src/workbench/stores/growthStore.js:60` — 漏 import，成长中心整页空

- 事实：本文件第 16 行只导入 `getTasksByStudent / getWrongQuestionsByStudent / getQuestionsByTask /
  getKnowledgeMastery`，从未导入 `getQuestionsByIds`。该符号在 `src/services/apiService.js` 有导出，
  `questionStore.js:3`、`reviewStore.js:3` 都正确导入了，只有 growthStore 漏。
- 用户可见后果：学生只要有任何带 `question_ids` 的任务，第 60 行必抛 ReferenceError → 落进第 65 行
  catch → 第 67-70 行把 `tasks / wrongQuestions / questions / knowledgeMastery` **全部重置为空数组**。
  即成长中心整页空白，控制台只留一行「加载成长中心数据失败」。
- 是否核心链路：教师工作台数据加载链，不在批改/错题写入链上。
- 修复：补一行 import。影响范围单文件，无兼容问题。验证：打开成长中心选一个有题目的学生，
  任务列表与题目列表都有数据。

### `src/workbench/stores/wrongBookStore.js:377,378` — catch 作用域，错题状态无法回滚

- 事实：`previousStates` 在 `batchUpdateStatus` 的 `try{}` 内第 351 行以 `const` 声明，
  第 372 行 `catch{}` 无法访问该块级作用域。
- 用户可见后果：批量标记错题「已掌握」先做乐观更新（355-356 行改 `wq.status`）；接口失败进入 catch 后，
  回滚语句自身抛 ReferenceError → 回滚永不执行，**前端显示「已掌握」而库里没写成功**。
- 是否核心链路：**是**——错题是长期学习数据（AGENTS.md 核心原则 2），且属错题生命周期，
  按禁止事项第 2 条必须你明确同意后才改。
- 修复：把 `const previousStates = new Map()` 提到 `try` 之前。
- 兼容策略：不改数据结构、不改接口，只修作用域；无历史数据迁移。
- 验证：批量标记时人为让接口失败（断网/mock 500），确认状态回到标记前，且不再抛 ReferenceError。

### `src/workbench/stores/reviewStore.js:1783` — 重复键，当前无功能影响

- 事实：第 1687 与 1783 行在同一 return 对象里重复展开同一变量，后者覆盖前者且值相同。
- 价值在物证：两处来自不同批次改动（1783 带 `[B2]` 注释），说明并发改动曾在同一核心文件上互不知情。
- 建议：删 1783 的重复项，行为不变。低优先级，但可作为「核心文件并发修改需串行」的实例留档。
