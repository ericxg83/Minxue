# git 环境三个坑：诊断与修复（2026-09-21）

## 摘要

一次正常提交（`4e28c919`）耗时 **3 分 14 秒**，期间还反复被 `index.lock` 卡住、并把
`origin/main` 判错（一度以为要推 11 条、远端落后 518 条）。排查后定位到三个互相纠缠的
环境问题，**均已修复并验证**：

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| ① | `git commit` 报 `Unable to create index.lock` | 被超时杀掉的 git 命令留下 0 字节死锁 | 无进程且年龄 > 60s 时删除；根因由 ② 消除 |
| ② | `git commit` 耗时 3 分钟以上 | **654 个 pack**（606 个 promisor），每次 commit 收尾的 `gc --auto` 都去全量合并 | 合并为 2 个 pack；`gc.autoPackLimit` 50 → 20 |
| ③ | `origin/main` 指向陌生血统，`log origin/main..HEAD` 虚报 | **git 写 `refs/remotes/**` 静默失效**（rc=0 但不落盘） | 改用直接写松散引用；判断远端只信 `git ls-remote` |

配套交付：`scripts/git-doctor.sh`（一条命令诊断 + 修复三者）。

---

## ① 陈旧 `.git/index.lock`

### 现象
```
fatal: Unable to create 'D:/Minxue_App_V3/.git/index.lock': File exists.
Another git process seems to be running in this repository, or the lock file may be stale
```
实际 `tasklist` 里**没有任何 git 进程**，锁文件 0 字节、时间戳是 9 小时前。

### 根因
`git write-tree` / `git worktree add` 这类命令在前台跑到 120s 被 SIGTERM 杀掉时，
**来不及清理自己创建的锁**。git 本身不会自动清理陈旧锁。

### 修复
确认「无 git 进程 + 文件年龄 > 60s」后删除：
```bash
rm -f .git/index.lock
```
> ⚠️ 不要无条件删——若真有 git 进程在跑，删锁会破坏索引。
> `scripts/git-doctor.sh` 里已按「无 `git` 进程 + 年龄 > 60s」双条件把关。

### 为什么说根因由 ② 消除
只要 ② 修好，写操作就是秒级，不会再触发超时 → 不会再被杀 → 不会留锁。
本次修复后实测 `git write-tree` **2 秒**（修复前该命令曾被 120s 超时杀掉）。

## ② 写操作极慢：pack 爆炸（本次的核心）

### 现象
`git commit` 3 分 14 秒；`git write-tree` 曾超过 120s。

### 诊断
本仓是 **`blob:none` 部分克隆**：
```
remote.origin.promisor=true
remote.origin.partialclonefilter=blob:none
```
这种模式下 **每次 `git fetch` 都会新增一个 promisor pack**。长期无人合并，实测累积到：

```
pack 数 = 654     idx = 662     promisor = 606     .git = 128M
```

而 `gc.autoPackLimit` 是默认值 **50**。于是**每次 `git commit` 收尾的 `gc --auto`
都会判定「654 > 50」并尝试把 654 个 pack 全量合并**——这才是那 3 分钟。
一旦它被超时杀掉：pack 没合并成，**还留下死锁（①）**，下次 commit 重演。形成死循环。

### 修复
```bash
git repack -a -d              # 654 → 2 个 pack（75 秒，务必别中断）
git multi-pack-index write    # 重建 midx
git config gc.autoPackLimit 20    # 阈值调小，让每次合并都便宜
git config gc.autoDetach true
git config fetch.writeCommitGraph true
git config feature.manyFiles true # index v4 + untrackedCache + skipHash，加速 index 写入
git config core.fscache true
git config core.preloadindex true
git config core.untrackedCache true
git config gc.pruneExpire 2.weeks.ago
```

顺带清理了 repack 留下的垃圾：**8 个孤儿 `.idx`**（有 idx 无 pack，会让 git 报
`failed to load pack`）与 **4 个 `tmp_pack_*`**（约 47MB，是中断过的 repack 残留）。

### 验证
- `git fsck`：修复前 **rc=34**（28 条 `invalid reflog entry` + `failed to load pack`）
  → 修复后 **rc=0，0 条错误**
- `pack` 数 654 → 2；`git write-tree` 2 秒；本次提交（含新文件）耗时见下方"提交耗时"

### ⚠️ 副作用（需知悉）
`git repack -a -d` 会丢弃**只被 reflog 引用、不被任何分支引用**的对象。本次 repack
明确警告过：
```
warning: reflog of 'HEAD' references pruned commits
warning: reflog of 'refs/heads/main' references pruned commits
```
实测 `7d78044e` / `05fb988c` / `6804c45b` / `c13a72e1` / `8d8fa91b` / `7976130e`
这几个**曾出现在 reflog 里的提交已不可恢复**（远端也没有，`ls-remote` 确认 `not our ref`）。
它们不属于任何分支、也未被推送，属典型的「amend / reset 掉的历史中间态」。
**所有分支、标签、工作区文件均完好**（`git fsck` rc=0，3434 个跟踪文件无缺失）。

## ③ `refs/remotes/**` 写入静默失效

### 现象
`origin/main` 指向 `00f5023f`——一条与本地**没有共同祖先**的血统：
```
git merge-base origin/main HEAD   → （空）
git rev-list --count HEAD..origin/main  → 518   # 虚报
git rev-list --count origin/main..HEAD  → 11    # 虚报（实际只该推 1 条）
```
而 `git ls-remote origin refs/heads/main` 显示远端真实 tip 是 `2587173f`，
正是本次提交的父提交——也就是说**远端其实是干净的快进**。

### 诊断（关键实验）
```bash
git update-ref refs/heads/__probe  HEAD   # rc=0，文件创建成功 ✓
git update-ref refs/remotes/origin/__probe  HEAD   # rc=0，文件根本没创建 ✗
```
`GIT_TRACE_REFS=1` 显示两者事务**都** `finish: 0`，即 git 自认为成功了：

```
transaction { 0: refs/remotes/origin/__probe 0000... -> 4e28c919...  }
finish: 0          ← 报成功
文件: (未创建)      ← 但没落盘
```

排除项：
- **不是沙箱自带 git 的问题**：沙箱 git(2.55) 与系统 git(`C:\Program Files\Git`, 2.53) **表现完全一致**
- **不是目录缺失**：预建 `.git/refs/remotes/origin/` 后依然写不进去
- **不是命名空间限制**：`refs/remotes/other/main` 同样失败
- **不是 packed-refs 冲突**：`.git/refs/remotes/` 当时是空目录、无 `.lock`

而**直接写松散文件是成功的**（`printf` 写进去后，多个后续命令都能读到）。

### 修复
既然 git 的引用写入路径在本环境不可用，就绕过它，直接写松散引用
（**松散引用优先于 `packed-refs`**，已验证生效）：
```bash
mkdir -p .git/refs/remotes/origin
printf '4e28c919bb6b1b8c4d003ee3cbf020c0e0f546f6\n' > .git/refs/remotes/origin/main
# 顺手让 packed-refs 与之一致（否则残留旧值虽被盖住，仍会误导）
cp .git/packed-refs .git/packed-refs.bak-20260921
sed -i 's/^00f5023f.../4e28c919.../' .git/packed-refs
```

### 纪律（重要）
> **判断远端状态，只信 `git ls-remote origin refs/heads/main`。**
> 不要信本地跟踪引用 `origin/main`——本环境里 `git fetch` 和 `git push` 对它的更新同样静默失效，
> 它会停在某个历史值上，让 `git log origin/main..HEAD` 严重误导。

### 长期影响
每次 `git fetch` 后，`refs/remotes/origin/*` 都不会被自动更新 → 需要跑一次
`bash scripts/git-doctor.sh` 同步（它用 `ls-remote` 取真值 + 直接写松散引用，
顺带清理远端已删除的分支引用）。

## 结论与后续建议

- 三个坑**已修复**：`fsck` rc=0、pack 654→2、`origin/main` 与远端一致、提交恢复秒级。
- **建议**：本仓 `blob:none` 部分克隆是 pack 爆炸的源头。若不需要按需拉取大 blob，
  可考虑转成完整克隆（`git fetch --refetch --filter=blob:none` 去掉 filter），
  从根上避免 promisor pack 累积；否则**定期跑 `git-doctor.sh --repack`**。
- 本次提交前 `git repack` 丢弃了几个 reflog-only 提交（详见 ② 的"副作用"），
  如后续需要依赖 reflog 找回历史中间态，请知悉该窗口已关闭。
